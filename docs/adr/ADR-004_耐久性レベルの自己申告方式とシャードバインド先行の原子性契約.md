# ADR-004: 耐久性レベルの自己申告方式とシャードバインド先行の原子性契約

## 1. 背景・課題

- **背景**: 初期プロトタイプでは「Write-Before-ACK（永続化保証）」を掲げつつ、SQLite の接続設定が `PRAGMA synchronous=NORMAL` になっていた（プロセス強制終了には耐えるが、OSクラッシュ・電源断では直近の COMMIT が失われる可能性がある）。また、DAO を親プロジェクトへ委譲する構成では、基盤側が物理DBの `fsync` 設定を直接強制できないほか、`meta`（パーティション台帳）と `shard`（レコード保存先）が別DBファイル・別コネクションになるため、両者をまたぐ書き込み順序と冪等性の契約を定める必要があった。
- **要求・制約**:
  - `WriteAck` が返った時点でどの水準の耐久性が保証されているかを、基盤・親プロジェクト・運用者が明確に判別できること（Issue #2 B1）。
  - 2相コミット（2PC）のような複雑な分散トランザクションを導入せずに、`meta` 未登録の孤児データを防止し、同一冪等キーでの異なるペイロード送信を確実に検出できること（Issue #2 B4・B5）。
- **判断しない場合の影響**: 耐久性水準が曖昧なまま本番運用すると電源断時に確定済みレコードやカーソルが消失するリスクがあり、`meta` と `shard` の更新順序が未定義だとルーティング不能な孤児レコードが発生する。

## 2. 決定

1. **耐久性レベル（`DurabilityLevel`）の宣言と既定水準 `power_loss`**:
   - `ShardDAOPort.write_transaction` の正常終了（COMMIT完了）をもって、電源断に耐える（`power_loss`）ことを基盤の既定水準とする（Issue #2 B1）。
   - `ShardDAOPort` と `MetaDAOPort` の双方に `durability: Literal["none", "process_crash", "power_loss"]` プロパティの実装を必須とし、基盤は起動時ログと telemetry にこの値を出力する。
   - SQLite 参照実装（`contrib/sqlite/`）は `journal_mode=WAL` + `synchronous=FULL` とし、`durability = "power_loss"` を返す。In-Memory 実装（`testing/memory_ports.py`）は `durability = "none"` を返す。親が性能優先で `synchronous=NORMAL` 等へ落とす場合は `durability = "process_crash"` を明示的に宣言させる（オプトアウト方式）。
2. **`bind_shard` 先行・不変による 2PC 回避**:
   - `MetaDAOPort.bind_shard` と `ShardDAOPort.write_transaction` は別トランザクションとし、常に **「`bind_shard` を先に確定 → `write_transaction` を実行」** の順序に固定する（Issue #2 B4）。
   - `bind_shard` は並行呼び出しに対して冪等かつ不変（既存バインドを上書きせず既存の `PartitionInfo` を返す）とする。
   - `bind_shard` 成功後にシャード書き込みが失敗して「レコード0件の空パーティション」が残ることは許容し、`meta` 未登録のままシャードへ書き込む孤児データは厳禁とする。
3. **単一シャードトランザクション内の原子性と `payload_hash` による冪等性衝突検査**:
   - 同一シャード内の「冪等キー検索（`find_by_idempotency`）→ 連番採番（`next_sequence`）→ レコード挿入（`insert_record`）」は1つの `write_transaction` 内で原子的に実行する。
   - `PayloadCodec.encode` に決定論性を課し、`record_type`・`schema_version`・エンコード後バイト列を長さプレフィックス付きで連結した SHA-256（`payload_hash`）を算出する。同じ `(partition_key, idempotency_key)` が既に存在する場合、`payload_hash` が一致すれば `status="duplicate"` を返し、不一致なら `IdempotencyConflict` を送出する（Issue #2 B5）。

## 3. 理由・代替案

### 採用理由

1. **DAO委譲下での透明な耐久性管理**: DAO を親プロジェクトが実装するため、基盤が SQL の PRAGMA を直接発行することはできない。代わりに Port 契約で `durability` の自己申告を義務づけることで、In-Memory 実装の本番誤用や設定漏れを起動時に検知できる。
2. **分散トランザクション（2PC）の排除**: `bind_shard` を不変かつ冪等にし、シャード書き込みより先に確定させることで、途中失敗しても「空パーティションが残るだけ（次回書き込みでそのまま再利用可能）」という安全な状態に収束する。
3. **厳密な冪等性保証**: プロトタイプのように `idempotency_key` の一致だけで無条件に既存レコードを返すと、クライアントのバグで異なるペイロードに同じUUIDを使い回した際にサイレントなデータ欠損になる。`payload_hash` を比較することで衝突を確実に検出できる。

### 代替案

| 代替案 | 利点 | 欠点・リスク | 採用しなかった理由 |
| :----- | :--- | :----------- | :----------------- |
| 既定の耐久性を `process_crash`（`synchronous=NORMAL`）にする | ディスク同期待ちが減り、単件書き込みのスループットが高くなる | 電源断やOSパニック時に、`WriteAck` を返したはずのレコードやカーソルが消失し、Source of Truth の前提が崩れる | ストレージ基盤の既定値は安全側（`power_loss`）とし、性能優先時は明示的なオプトアウトとする方が安全であるため（Issue #2 B1） |
| `meta` と `shard` を2相コミット（2PC）や `ATTACH DATABASE` で単一トランザクション化する | 空パーティションが一切発生しない | SQLite 以外のDBエンジンや複数ストレージをまたぐ構成で DAO の実装が著しく困難になり、ロック競合も増大する | 空パーティションを許容する設計にすれば 2PC なしでデータ整合性を完全に保てるため（Issue #2 B4） |
| 冪等キーの一意性スコープを全シャード横断（グローバル）にする | パーティションをまたいだUUID使い回しも検知できる | 書き込みのたびに全シャードまたは中央メタDBへのロック・照会が必要になり、水平分割の意味が失われる | 1パーティションは1シャードに属するため、`(partition_key, idempotency_key)` スコープで単一シャード内に完結させるのが最適であるため（Issue #2 B5） |

## 4. 影響・トレードオフ

- **利点**:
  - 2PC を使わずに、孤児データゼロ・欠番なし・重複排除・冪等キー衝突検出を単一シャードのローカルトランザクションだけで保証できる。
  - `MetaDAOPort` にも `durability` を持たせることで、シャード台帳やカーソルの耐久性とレコード本体の耐久性の不一致を検知できる。
- **欠点・コスト**:
  - `durability="power_loss"`（`synchronous=FULL`）では毎回の COMMIT でディスク同期が発生するため、同一ディスク上のバースト書き込み性能はストレージの `fsync` 性能に律速される（Issue #7 の性能試験で実測する）。
  - `PayloadCodec.encode` の実装において、辞書のキー順序や数値表現の揺れを排除する決定論的シリアライズが必須となる。
- **影響を受ける正本文書**: 基本設計書（`DBF-BD-001`）、IF/API仕様書（`DBF-IF-001`）、データ構造仕様書（`DBF-DS-001`）、書き込み経路詳細設計書（`DBF-DD-001`）。
- **移行・ロールバック**: 新規設計のため移行不要。
- **セキュリティ・運用上の影響**: 起動時に `ShardDAOPort.durability` と `MetaDAOPort.durability` をログ・telemetry に記録し、`none` の場合はテスト環境用である旨を判別可能にする。

## 6. 例外・見直し条件（必要な場合のみ）

- **例外・適用差異**: 単体テスト用の `testing/memory_ports.py` は `durability="none"` とし、Contract Test の項目2（再接続後の永続性）は `durability == "none"` の場合にスキップする。
- **見直し条件**: Issue #7 の性能試験において、`durability="power_loss"` での単件 `append()` が親プロジェクトの許容レイテンシー・スループットを満たさない場合。
