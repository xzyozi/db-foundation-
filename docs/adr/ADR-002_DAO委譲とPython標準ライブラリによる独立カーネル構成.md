# ADR-002: DAO委譲とPython標準ライブラリによる独立カーネル構成

## 1. 背景・課題

- **背景**: 親プロジェクト（アプリケーション本体）と物理DB群の間で、冪等性制御、パーティション別単調増加採番、Write-Before-ACK、非同期Pub/Sub配信、カーソルベース差分同期を共通化する汎用データ基盤（`storage_kernel`）を構築するにあたり、基盤の提供形態・ストレージとの関係・実装言語・外部依存方針を決定する必要があった。
- **要求・制約**:
  - 親プロジェクト側でテーブル構造、SQL、DBドライバー（SQLite / PostgreSQL / DuckDB 等）を自由に選択・設計できること（DAOの自由度）が必須要件である（Issue #1 A4）。
  - Gitサブモジュールとして親リポジトリにそのまま組み込め、依存衝突やライセンス汚染を引き起こさないこと（Issue #1 A4・A5）。
- **判断しない場合の影響**: 基盤内部に特定DBエンジンや外部ライブラリを密結合させると、親プロジェクト側のスキーマ設計やドライバー選定を拘束し、サブモジュールとして再利用できなくなる。

## 2. 決定

1. **Ports & Adapters（ヘキサゴナルアーキテクチャ）によるDAO委譲**:
   - 外部ブローカー型OSSを採用せず、ストレージアクセス（DAO）を親プロジェクトへ委譲する薄い独立カーネル（`storage_kernel`）を自作する。
   - カーネル本体（`core/`・`runtime/`）は抽象契約（`ports/`・`contracts/`）のみに依存し、具象ストレージ製品やSQL文を一切関知しない。
   - サブモジュールには単体テスト・契約検証用のIn-Memory実装（`testing/memory_ports.py`）と、外部依存ゼロのSQLite参照実装（`contrib/sqlite/`）を同梱する。`core/` から `contrib/` は import しない。
2. **Python標準ライブラリのみによる純粋実装（FFI不採用）**:
   - 実装言語は Python（`>=3.10`）とし、`contracts/`・`ports/`・`core/`・`runtime/`・`testing/`・`contrib/sqlite/` はすべて Python 標準ライブラリのみで実装する。
   - 型契約は `typing.Protocol` と静的型検査（`mypy` strict）で担保し、実行時のDAO不変条件は `unittest` ベースの Contract Test（`testing/contract_test.py`）で担保する。
   - Rust / C++ によるコア実装と FFI バインディング構成は採用しない。
   - ライセンスは Apache-2.0 とし、DBドライバー固有のライセンスは親プロジェクトの Adapter 側に隔離する。

## 3. 理由・代替案

### 採用理由

1. **DAOの自由度とトランザクション制御の両立**: `ShardDAOPort` / `ShardTxPort` / `MetaDAOPort` を `typing.Protocol` として定義することで、親プロジェクトが独自のテーブル設計・DBエンジンを用いつつ、基盤側で「重複検査 → 採番 → 書き込み」の原子性と順序保証を制御できる。
2. **コールバック境界の単純性**: Write-Before-ACK を実現するため、カーネルから親側の `ShardTxPort` メソッドをトランザクション内で呼び出す逆方向コールバックが毎回発生する。同一言語（Python）内であれば、例外変換・コンテキストマネージャ・ジェネリクス（`RecordEnvelope[T]`）をオーバーヘッドなく安全に扱える。
3. **ゼロ依存による高い移植性**: 実行時依存を標準ライブラリのみに限定し、`contract_test.py` も標準の `unittest` ベースで記述することで、親プロジェクトの仮想環境やパッケージ構成と一切衝突しないサブモジュール運用が可能になる。

### 代替案

| 代替案 | 利点 | 欠点・リスク | 採用しなかった理由 |
| :----- | :--- | :----------- | :----------------- |
| 外部ブローカー型OSSの採用（NATS JetStream / Kafka 等） | 既存の成熟した分散ログ・Pub/Sub機能をそのまま利用できる | ストレージ実装をブローカー内部に抱え込むため、親プロジェクトがテーブル構造・SQL・DBドライバーを自由に決めることができない。別プロセス常駐も必要になる | 「DAOの自由度」および「単一プロセス・ローカルアプリでの軽量組み込み」（Issue #1 A1・A2・A4）という必須要件と合致しないため |
| コアを Rust / C++ で実装し Python から FFI（PyO3 等）で呼び出す構成 | コア制御のCPU処理速度やメモリ効率を高められる、他言語バインディングへの展開余地がある | Write-Before-ACK のたびにコアから親側 Python の `ShardTxPort` を呼ぶ逆方向コールバックが発生し、FFI境界でトランザクション・例外・ジェネリクスを往復させる設計・ビルド・デバッグコストが過大になる | ボトルネックはディスク I/O（`fsync`）であり、FFI境界の複雑化に見合う利点がないため（Issue #1 A5） |
| サードパーティ製ORM / バリデータ（SQLAlchemy / Pydantic 等）への依存 | モデル定義やDB接続抽象化の記述量を減らせる | 親プロジェクト側で使用するライブラリやバージョンと衝突しやすく、サブモジュールとしての独立性が損なわれる | サブモジュール単体で外部依存ゼロで完結させる方針（Issue #1 A5）に反するため |

## 4. 影響・トレードオフ

- **利点**:
  - 親プロジェクトは任意のDBエンジン・スキーマを採用でき、`ShardDAOContractTest` を継承するだけで基盤の不変条件を自動検証できる。
  - サードパーティ依存の脆弱性対応やバージョン非互換の影響をカーネル本体が受けない。
- **欠点・コスト**:
  - 親プロジェクト側で `ports/` に準拠した DAO Adapter と `bootstrap.py`（DI組み立て）を実装する必要がある。
  - 複数プロセスや他言語からの直接呼び出しには対応しない（将来必要になった場合は `ports/transport.py` 経由の IPC デーモン構成へ拡張する）。
- **影響を受ける正本文書**: 基本設計書（`DBF-BD-001`）、環境・開発基盤仕様書（`DBF-ENV-001`）、IF/API仕様書（`DBF-IF-001`）。
- **移行・ロールバック**: 新規設計のため既存データ移行は不要。将来他言語対応が必要になった場合は、コアを書き換えずに `ports/transport.py` の IPC ラッパーを追加する。
- **セキュリティ・運用上の影響**: 外部パッケージを含まないためサプライチェーンリスクが最小化される。
