# ADR-006: main へはリリースブランチ経由のスカッシュで取り込む運用

## 1. 背景・課題

- **背景**: v1.0.0 のリリースで、`develop` を `release/v1.0.0` 経由で `main` に取り込んだ。このとき、マージ方法を「マージコミット」にしたが、`main` の履歴をどう扱うかは、方針として決めていなかった。
- **要求・制約**:
  - 親プロジェクトは、`main` のタグ（`vMAJOR.MINOR.PATCH`）でサブモジュールを固定する（`DBF-ENV-001` §4.3）。`main` には、リリースの単位が分かる形で履歴が残ってほしい。
  - 個々の変更（観点ごとのコミットと、`(#番号)` による Issue との対応）の履歴は、`develop` で管理できれば足りる。
- **判断しない場合の影響**: リリースのたびに、`main` への取り込み方が揺れ、`main` の履歴と `develop` の履歴の関係が不明確になる。

## 2. 決定

1. **`main` への変更は、リリースブランチ経由に限る**: `develop` から `release/v<MAJOR.MINOR.PATCH>` を切り、`release/` → `main` の PR で取り込む。`develop` → `main` の直接の PR は行わない。緊急の不具合修正（`hotfix/`）だけが例外で、`main` から分岐して `main` へ戻す。
2. **`release/` → `main` は、スカッシュ（Squash and merge）で取り込む**: `main` には、リリースごとに 1 コミットが積まれる。コミットメッセージは `[docs] v<バージョン> リリース` のように、バージョンを含める。
3. **詳細な履歴は `develop` で管理する**: 観点ごとのコミット、`(#番号)`、PR のマージコミットは `develop` に残る。`main` の 1 コミットから、詳細な履歴をたどる必要があるときは、`CHANGELOG.md` と、リリース PR の本文、`develop` の履歴を参照する。
4. **スカッシュ後は、`main` を `develop` へマージして戻す**: スカッシュで作られた `main` のコミットは、`develop` の履歴とつながらない。マージして戻すことで、履歴をつなぐ。これは**リリースのたびに必須**とする。

## 3. 理由・代替案

### 採用理由

1. **`main` の一覧性**: リリース 1 回が 1 コミットなので、`main` の履歴が、リリースの一覧になる。親プロジェクトが、どのタグ間で何が変わったかを追いやすい。
2. **履歴は失われない**: 詳細な履歴は `develop` にすべて残る（`main` に 1 コミットにまとめても、`develop` の履歴は変わらない）。
3. **リリースブランチの意義**: リリース準備（バージョン、CHANGELOG、設計書の状態の更新）を、`develop` を汚さずに行い、品質ゲートを通してから `main` に入れられる。

### 代替案

| 代替案 | 利点 | 欠点・リスク | 採用しなかった理由 |
| :----- | :----- | :------------- | :----------------- |
| `release/` → `main` を**マージコミット**で取り込む | 観点ごとのコミットと `(#番号)` が `main` にも残る。`main` と `develop` の履歴が自然につながり、戻しの手順も省ける（v1.0.0 で採用した方法） | `main` の履歴が、`develop` と同じ量になり、リリースの一覧として読みにくい | `main` はリリースの単位で読めればよく、詳細は `develop` で足りるため |
| `develop` → `main` を直接スカッシュで取り込む | リリースブランチが不要で、手順が短い | リリース準備のコミットを `develop` に入れるか、`main` への PR に混ぜる必要がある。品質ゲートの確認の場所が曖昧になる | リリース準備を、独立したブランチで行うため（採用理由 3） |
| `develop` を `main` へ早送りで取り込む | 履歴が一本になり、戻しも不要 | リリースの区切りが、履歴に現れない | リリースごとの 1 コミットという一覧性が得られないため |

## 4. 影響・トレードオフ

- **利点**: `main` がリリースの一覧になる。親プロジェクトが、タグ間の変更を追いやすい。
- **欠点・コスト**: リリースのたびに、`main` を `develop` へマージして戻す手順が増える。忘れると、次のリリースの PR に、前回の変更が差分として再び現れ、衝突することがある。
- **影響を受ける正本文書**: Git Flow 運用規約・リリース手順（`docs/setup/git_flow_and_branch_policy.md`）。バージョンとタグのルール（`DBF-ENV-001` §4.3）は変わらない。
- **移行・ロールバック**: v1.0.0 は、マージコミットで取り込まれており、書き換えない（`main` の履歴は変えない）。次のリリースから、スカッシュを適用する。
- **セキュリティ・運用上の影響**: 特になし。

## 6. 例外・見直し条件

- **例外・適用差異**: v1.0.0 は、マージコミットで `main` に取り込まれている（この ADR の決定前）。`hotfix/` は、`main` から分岐し、`main` へ戻す（スカッシュ可否は、そのときの変更量で決める）。
- **見直し条件**: 次のいずれかが起きたとき。
  - 戻しの手順の漏れで、衝突が繰り返し起きる
  - `main` の 1 コミットから、詳細な履歴をたどる必要が頻繁に生じる
  - 複数人で開発するようになり、`main` 側で詳細な履歴の確認が必要になる
- **見直し時期**: 見直し条件を満たしたとき
