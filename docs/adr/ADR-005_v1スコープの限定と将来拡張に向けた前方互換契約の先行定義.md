# ADR-005: v1スコープの限定と将来拡張に向けた前方互換契約の先行定義

## 1. 背景・課題

- **背景**: 構想段階では、動的パーティション移動（`migrating`）、大容量データの外部退避（`BlobStorePort`）、自動スナップショット生成、古いログの自動削除（Retention）、一括書き込み（`append_batch`）、揮発データ管理（`ephemeral`）、アクセス制御・レート制限（`guard`）、プロセス間通信（`transport`）など多くの機能が挙げられていた。
- **要求・制約**:
  - 初期リリース（v1）は単一プロセス・ローカルアプリで通常規模（1パーティション数十万件、ペイロード最大64KB）を確実に動かすことが最優先であり、未確定の複雑な運用機能を早期に Port 契約へ固定すると、親プロジェクトの DAO 実装と Contract Test の負担が過大になる（Issue #1 A3、Issue #3 C1、Issue #4 D1、Issue #6、Issue #10 E2）。
  - 一方、サブモジュール運用の原則として `ports/` と `contracts/` の破壊的変更は Major バージョンアップになるため、v2 で確実に必要となるデータ項目や例外型を後から追加すると互換性が壊れる（Issue #4 D1）。
- **判断しない場合の影響**: v1 に全機能を詰め込むと設計・実装・テストが肥大化してリリースが遅延するか、逆に何も考慮せずに削ると v2 で `RecordEnvelope` や公開例外の破壊的変更が発生する。

## 2. 決定

1. **v2 以降へ先送りする機能（v1 の対象外）**:
   - **パーティション移動**: `migrating` 状態、`Migratable*Port`、`migrate_partition`（コピー検証、キャッシュ無効化、CAS 切り替えを v2 で一体設計する。Issue #3 C1）。
   - **大容量 Blob 退避**: `BlobStorePort`、`RecordEnvelope.blob_refs`。v1 は 64 KB 上限とし、超過時は `PayloadTooLarge` で拒否する（Issue #1 A3）。
   - **スナップショット自動生成・自動 Retention・自動 VACUUM**: `delete_through`、Retention 対象 Consumer 登録簿、最古保持 `seq` 管理。これらは無期限保持を前提とする v1 では実装せず、v2 で一体設計する（Issue #4 D1）。
   - **バッチ書き込み（`append_batch`）**: v1 の書き込み API は単件の `append()`（および `write_snapshot()`）のみとする。将来必要になった場合も既存の `ShardTxPort` を変えずに公開 API のみ追加する（Issue #6）。
   - **揮発データストア（`core/ephemeral.py`）およびアクセス制御・レート制限（`ports/guard.py`）**: 単一プロセス・ローカルアプリでは親プロジェクト側のメモリ管理で十分であり、ACL やレート制限の必要性も低いため、v1 ではファイルを作成せず対象外とする（Issue #10 E2）。
   - **IPC / RPC 配信口（`ports/transport.py`）**: マルチプロセス・他言語対応が必要になる v2 以降の拡張口として名前のみ予約し、v1 では定義しない（Issue #1 A1・A2）。
2. **Major バージョンアップを避けるため v1 で先行定義する契約**:
   - **パーティション状態管理**: `PartitionStatus = Literal["active", "read_only"]`、`set_partition_status`、`list_partitions` を v1 で導入し、軽量な書き込み停止と起動時キャッチアップを実現する（Issue #3 C1・C5）。
   - **スナップショットの手動書き込みと予約種別**: `record_type="__snapshot__"` をシステム予約（`"__"` 始まりを通常 `append` で拒否）とし、手動の `write_snapshot`、`RecordEnvelope.covers_through_seq`、`register_projection(..., include_snapshots=False)` を v1 で提供する（Issue #4 D1）。
   - **期限切れカーソル例外の契約定義**: `CursorExpiredError` を `contracts/errors.py` に先行定義する。v1 では Retention を行わないため送出されないが、呼び出し側が「期限切れ時は最新スナップショットから再開する」エラーハンドリングを最初から組めるようにする（Issue #4 D1）。
   - **メンテナンスモードと読み取り時 Upcast**: バックアップ整合点を作る `enter_maintenance` / `exit_maintenance`（`MaintenanceHooks`）と、保存済みレコードを書き換えずに旧版バイト列を1版ずつ進める `PayloadUpcaster` を v1 に含める（Issue #4 D2・D3）。

## 3. 理由・代替案

### 採用理由

1. **親プロジェクトの DAO 実装負荷の最小化**: v1 の `ShardDAOPort` / `MetaDAOPort` を最小限のプリミティブに絞ることで、親プロジェクトが独自 DAO を実装し13項目の Contract Test を通すハードルを大幅に下げられる。
2. **`fetch_range` の「欠落なし」契約の保護**: Retention（削除）を中途半端に入れると、`fetch_range` の欠落なし契約と衝突する。削除操作・Consumer 登録簿・最古保持 `seq` 判定は v2 で一体として導入し、v1 では `__snapshot__` と `CursorExpiredError` の型契約だけを先行固定するのが最も安全である。
3. **前方互換性の確保**: `RecordEnvelope` のフィールド（`schema_version`, `payload_hash`, `covers_through_seq`）と標準例外（`CursorExpiredError`, `ReservedRecordTypeError` 等）を v1 で確定させておくことで、v2 での機能追加を後方互換（Minor バージョンアップまたは拡張 Port の追加）で行える。

### 代替案

| 代替案 | 利点 | 欠点・リスク | 採用しなかった理由 |
| :----- | :--- | :----------- | :----------------- |
| パーティション移動・Retention・Blob退避・`ephemeral`・`guard` をすべて v1 で実装する | v1 から大規模・長期運用・マルチテナント制限まで完結する | DAO Port のメソッド数と Contract Test が倍増し、まだ具体的な要求がない機能のために v1 の設計と実装が複雑化する | 現時点の想定規模（1パーティション数十万件、単一プロセス）では不要であり、YAGNI 原則に反するため（Issue #6、Issue #10 E2） |
| スナップショットや `CursorExpiredError`、Upcast もすべて v2 まで一切定義しない | v1 の `contracts/` をさらに小さくできる | v2 でスナップショットや Retention を導入する際に `RecordEnvelope` や例外体系に破壊的変更が生じ、親プロジェクト側のコード修正（Major 更新）が必要になる | 後から追加すると `contracts/` の破壊的変更になる要素だけは v1 で先行定義しておく方が長期的な保守性が高いため（Issue #4 D1・D3） |

## 4. 影響・トレードオフ

- **利点**:
  - v1 のアーキテクチャと設計書（BD / IF / DS / DD）がシンプルで検証しやすい構成になる。
  - 将来 `append_batch()` や Retention、パーティション移動を追加する際、既存の `ShardDAOPort` / `contracts` を壊さずに拡張できる。
- **欠点・コスト**:
  - v1 ではレコードを自動削除しないため、1パーティションが数百万件を超えて継続増加するワークロードにはそのままでは適用できない（必要に応じて親が `write_snapshot` を呼び、v2 で Retention を導入する）。
  - 64 KB を超えるペイロードは基盤へ直接書き込めないため、親プロジェクト側で分割または外部ファイル管理を行う必要がある。
- **影響を受ける正本文書**: 基本設計書（`DBF-BD-001`）、IF/API仕様書（`DBF-IF-001`）、データ構造仕様書（`DBF-DS-001`）、各詳細設計書（`DBF-DD-001`〜`004`）。
- **移行・ロールバック**: v1 で保存されたレコードやスナップショットは、`schema_version` と `PayloadUpcaster` により v2 以降もそのまま読み取り・移行できる。
- **セキュリティ・運用上の影響**: バックアップ時は `enter_maintenance` で書き込みを停止して整合点を作り、親プロジェクトの DAO がファイルコピーとマニフェスト検証を行う。
